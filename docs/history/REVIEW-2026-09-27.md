# valvur: a first-principles review

**Date:** 2026-09-27. **Tree:** `main` at `fbe2dab` (version `1.0.0`, unreleased). **Scope:** the
whole product, judged against one goal: from Claude Code or Kiro, one request scans the project
and writes a report into it that is fast, complete or honest about why not, and trustworthy.
Local only. **Status:** accepted by the owner on 2026-09-27, section 11 included. The task
list's Phases R0 to R8, built unattended, and the rewritten `CLAUDE.md` follow from it.

**Method.** I read the scan path end to end (`api.py`, `runner.py`, `exclusions.py`, the
adapters, `mcp/jobs.py`, `mcp/server.py`, `operations.py`), both gate reports and the owner's
newer copy of the second one, the pre-publication audit of `occams-test-lab`, the corpus
report, and the test suite's structure. I checked Anthropic's Claude Code MCP documentation for
how the primary client treats long tool calls. I measured on this Mac, and planted two small
trees to test exclusion behaviour. Every number is in the appendix with its conditions. The
machine had 11 GB of its 12 GB swap in use and a load average of 5.5, so absolute times are
pessimistic. The comparisons were run back to back and are fair.

---

## 1. Verdict

**The contract is right and the engine is wrong.** The parts that decide what a report *means*
are well designed and should be kept: per-class fingerprints, the three statuses, *not
re-checked*, one generation per results folder, coverage notes, fenced evidence, the offline
guarantee and the release pipeline. The parts that decide how a scan *runs* produce most of
the failures of the last ten days, and they will keep producing them.

**Three design choices in the engine generate the defect stream.** Each gate and review has
found new symptoms of the same three causes. Each was fixed locally, and each fix added state
that the next gate found a way around.

| root cause | what it produced (task or gate item) |
|---|---|
| **One container per Scanner, scheduled by host threads** | 16.2, 23.3.3, 23.3.7, 26.0.2, 27.1.1, 28.0.3, 29.0.2, 29.1.3, C1 |
| **The live working tree is bind-mounted, and exclusion is translated into six flag dialects** | B1, B3, 29.0.1, 29.1.1, 29.1.2, C9, and two new silent misses below |
| **A start-and-poll MCP protocol, built on a timeout the primary client does not have** | 10.2.5, 26.4.1, 29.0.4, 29.2.4, C3, C4, C7 |

**The process amplifies this.** Three reviews and two gates in eight days became five phases
of local fixes. Nothing stepped back to ask whether the engine's shape was the problem. Tests fake
the runtime in ways that cannot show these defects, and the macOS path, where the users are,
is never tested automatically.

**Recommendation in one line:** keep the contract, rebuild the execution layer around one
container per scan fed a snapshot of the files git would publish, make `scan` one blocking call,
and do not tag `1.0.0` until an acceptance set passes on a Mac.

## 2. What the product has to do, from first principles

The goal decomposes into eight properties. Everything below is judged against them.

| # | property | today |
|---|---|---|
| R1 | **Scan the code the user means**: what git would publish, plus history for secrets | scans the working tree; history never read |
| R2 | **Fast enough that nobody tunes anything**: under a minute on a Mac warm, three cold | 20 s on a clean tree; failure or 30 minutes on a real checkout until excluded by hand |
| R3 | **One call from the agent** | six status polls and five shell calls in the agent pass |
| R4 | **Every stop is total and confirmed**: cancel, timeout, crash, client death | C1: Scanners launch after a cancel; an orphaned server holds the lock |
| R5 | **The report is complete or says so, grouped, and names its scope** | complete-or-says-so is good; no grouping; scope not stated; two silent misses |
| R6 | **Bad input fails at the call, in plain words** | C2, C3 |
| R7 | **Offline and provable** | met, and the best-built part of the product |
| R8 | **Fresh data without a terminal** | a clean result turns *inconclusive* after 7 days and no MCP tool can refresh |

## 3. The three engine causes, with evidence

### 3.1 One container per Scanner, scheduled by host threads

`api._fleet` submits every Scanner to a `ThreadPoolExecutor` up front. Each worker runs a
blocking `docker run` through `subprocess.run`. Stopping a scan therefore means reconciling
three things that change independently: futures still queued, clients still blocked, and
containers the daemon owns. The code carries a cancel flag, a per-runner name registry, a
process-wide registry, a budget path that cancels futures, a cancel path that does not, a
timeout path that kills by name and polls until gone, and a server exit path that sweeps. C1 is
the gap between two of those paths. The next gap will be another pair.

A second cost is memory. Each container gets a 2 GiB ceiling, a 4 GB Docker Desktop VM cannot
hold six of them, and 29.1.3 narrowed the fleet to two at a time. Narrowing created the queue that C1
lives in.

**Measured on the lab's 312 source files, this Mac:** valvur's fleet took **20.3 s**. The same
six tool invocations run in parallel inside **one** container took **7.4 s and 8.3 s**. The
work is identical. The difference is container starts, the two-wide queue, and per-container
overhead.

### 3.2 The live working tree is mounted, and exclusion is six dialects

Every Scanner walks `/workspace` itself, through Docker Desktop's file sharing. Listing the
lab's 109,521 files takes **1.6 s on the host and 16.6 s through the bind mount**, and each
Scanner pays it again. `git ls-files -co --exclude-standard` lists the 312 files that matter in
**0.03 s**. The first gate's failure was mostly this.

Exclusion then has to be expressed in each tool's own language: Trivy globs, Checkov regular
expressions, Syft globs, Opengrep component patterns, OSV-Scanner names or regexes, and a
generated Gitleaks config that must extend the project's own. These flags were written on
2026-08-31 and called by nothing until 2026-09-26. This review found that they still disagree:

- **New defect N1: one exclude, two meanings.** `[scan] exclude = ["archive"]` means the
  top-level `archive/` to Gitleaks, Trivy and Syft, and **any directory named `archive`** to
  Opengrep, Checkov and OSV-Scanner. Measured with a planted tree: Opengrep never reported the
  shell-injection flow in `src/archive/b.py`. The report lists `archive` as excluded and says
  nothing about `src/archive/`.
- **New defect N2: the built-in skip list hides first-party code, silently.** `VENDORED`
  includes `build`, `out`, `dist`, `target`, `external`, `vendor` and `.cache` at any depth.
  Since 29.0.1 they are skipped before any Scanner reads them, so `vendored_dropped` has
  nothing left to count. Measured: `mypkg/build/steps.py` with a planted shell-injection flow
  was not scanned by any Scanner. The run said *2 active* and `SUMMARY.md` never mentions a
  skipped directory. This is the "clean scan of a vulnerable repository" class that
  `CLAUDE.md` calls the worst possible failure.

### 3.3 Start-and-poll, on a false premise

`mcp/jobs.py` opens with the reason for polling: *many MCP clients time out at 30-60 [seconds]*.
For the two clients this product targets, that is not true today:

- **Claude Code** gives a stdio tool call a **30-minute idle window**, and progress
  notifications count as activity. The wall-clock default is about 28 hours. A call still
  running after **two minutes moves to a background task** instead of blocking the session.
  It also sets `CLAUDE_PROJECT_DIR` for the server and answers `roots/list`.
  Source: code.claude.com/docs/en/mcp.
- **Kiro** enforces a startup timeout and, per its issue tracker, no per-call timeout
  (kirodotdev/Kiro#8111). This is not measured here.
- Claude Code forwards only `structuredContent` to the model when both forms are present
  (anthropics/claude-code#55677), which is what 29.2.4 found by measurement.

What polling costs: the agent pass made **16 turns for $1.08**, with one `scan`, six
`scan_status`, five shell calls it wrote to wait, and one `list_findings`. The status reply has
grown field by field (`waited_s`, `completed`, `now`, `finished_scanners`, `budget`, `next`,
`advice`, `doctor_may_help`), and C4 and C7 are fields that disagree with the state or the text.

## 4. Other findings of this review

- **N3: the seven-day trap.** The database is stale after 7 days (`DB_STALE_AFTER_DAYS`), a
  stale database makes any nil result *inconclusive*, a scan never refreshes stale data, and
  none of the six MCP tools can. An agent-only user who scans a clean project a week after
  installing gets *inconclusive* and cannot fix it without a terminal.
- **N4: git history is never scanned (the owner's C10).** Gitleaks runs in `dir` mode and the
  image has no `git`. The README's tool table says *"Secrets, including git history"*
  (`README.md:432`). The test suite locks the defect in: the argv snapshot pins `dir`, and the
  e2e fixture has no `.git`. `git` is GPL-2.0, so ADR-0005 forbids adding it to the image.
- **N5: the workspace argument is unrestricted.** Any path is accepted, a results folder is
  created there, and `list_findings` reads any `findings.json`. C2 is one case of it.
- **The report is instrument output, not an assessment.** On the lab, `SUMMARY.md` opens with
  30 lines of instructions to agents before any finding. It lists one rule eight times with
  titles cut mid-word. It does not say what was scanned. The owner's manual pre-publication
  audit of the same repository found four medium issues, and valvur reported one of them. Two
  of the other three sit squarely inside valvur's own positioning: an untracked `.mcp.json`
  holding a private path and not gitignored, and `.claude/settings.local.json` not ignored.
  The audit also found, at low, workflow permissions wider than needed, which is a standard
  GitHub Actions check.
- **Checkov is the slowest Scanner everywhere and finds little outside Terraform.** In the
  corpus report it is the slowest on 12 of 12 repositories. On the 11 application repositories
  it produced 5 findings in total, all GitHub Actions checks. On the lab it took 14.4 s of a
  20 s scan for two workflow files and found nothing, including the top-level `pages: write`
  permission the manual audit flagged.
- **The AI-specific checks found nothing on real code.** Dependency reality, the AI Artifact
  Check and the taint rules produced zero findings across the thirteen-repository corpus. That
  is expected for real projects and fine, but it means what users actually receive is standard
  scanner output, and its quality is the product.

## 5. Recommendations: the engine

### E1. One scan runs in one container

An in-image runner, `python -m valvur.engine`, receives a plan and runs the tools as child
processes in parallel, each in its own process group with its own timeout. It streams progress
as JSON lines on stderr and leaves each tool's report and a manifest (exit code, duration,
stderr tail, whether it timed out) in its output. valvur's Python already ships in the image for
the Checks, so this adds a module, not a dependency.

The host launches one container, reads progress, enforces one deadline, and on cancel runs one
`kill` and one `wait`. `CANCELLED` is reported only once the runtime confirms the container is
gone. The thread pool, the queue, both name registries, per-Scanner kill-and-poll, and the
fleet width all go away, and with them C1's class of race.

- `offline` is one container with no network. `full` adds a second container, with network,
  for only the Scanners that need it, so ADR-0010's per-Scanner least privilege holds.
- One memory ceiling for the scan, sized from the runtime, replaces six.
- This is `PROTOCOL.md` version 2. ADR-0001's principle, a thin host shim and a sealed
  container, is unchanged; its implementation detail, one container per Scanner, changes.
- Expected effect, from the measurement above: about 20 s down to 8 to 10 s on this Mac for
  the same tree, and one thing to stop.

### E2. Scan a snapshot of the files, not a mount of the tree

The host builds the file list, streams it as a tar into the container, and the tools read a
native in-VM filesystem.

- **Default scope is the git view:** tracked files plus untracked files git does not ignore.
  A directory that is not a git repository falls back to the walk, with a file-count ceiling
  that refuses before any Scanner starts and names the directory to exclude.
- `[scan] exclude` removes entries from the list. **Exclusion becomes one mechanism**, applied
  once, identical for every tool. The six dialects, the generated Gitleaks config and N1 go
  away. The built-in skip list goes away with them, because the git view already leaves out
  `.venv`, `node_modules` and build output in every repository that ignores them, which fixes
  N2.
- **Local agent configuration is always included**, even when ignored: `.mcp.json`,
  `.claude/`, `.kiro/settings/`. These are what the developer's own agent runs, and they are
  where the audit's findings were.
- **The report states its scope** as a manifest: *scanned 312 files, 3.4 MB, the git view;
  2 ignored paths not scanned*, with the list's hash in `run.json`.
- The container never sees the source tree, which is stronger than a read-only mount. The
  SELinux relabel question (ADR-0017), Podman's shared-path problem on macOS and the
  unreadable-workspace probe container all disappear for the workspace.
- Limits to design for: a tmpfs counts against the container's memory, so a large source set
  goes to a per-scan volume that is removed afterwards. Symlinks, submodules and LFS pointers
  need explicit rules.

This replaces the `honour_gitignore` opt-in with a `scope = "git" | "tree"` setting. It needs
an owner decision and an ADR, because `CLAUDE.md` §7 reads *exclusion is never a built-in
default*. The git view excludes nothing the project tracks, tests included, which is what that
rule protects.

### E3. Secrets in history, without GPL in the image

Correct the README now. Then have the host, which already runs `git` for the gitignore
opt-in, write `git log -p --all` with commit markers into the scan's input. Gitleaks scans it
as text, and the adapter maps each hit back to its commit. Offer it as `history = true`, on by
default for the "before publishing" use. Measure the cost on this repository and the lab
(219 commits) before choosing the default.

### E4. The Scanner set, decided by a spike on the corpus

*Amended by the measurement in 11.6:* Trivy found 3 of Checkov's 9 rules on
`terraform-aws-vpc`, so Checkov stays for infrastructure and zizmor takes the workflows.
KICS remains the one candidate to replace it outright.

- **Replace Checkov** with Trivy's misconfiguration scanner for infrastructure, which is the
  same binary already in the image, and **zizmor** for GitHub Actions. zizmor is MIT-licensed,
  written in Rust and has an offline mode. It covers unpinned actions, excessive permissions
  and template injection, which is the class the audit found and Checkov missed. ADR-0019 names
  this condition for reopening: *a faster IaC scanner under an acceptable licence*. The spike
  measures findings parity on `terraform-aws-vpc` and time on all thirteen repositories.
- **Produce the SBOM from Trivy's own pass** and drop Syft, if CycloneDX output from the
  filesystem scan matches today's content.
- **Move the action-pinning rule to zizmor** if parity holds. It is 64 of Opengrep's 71 corpus
  findings. Opengrep keeps the sink inventory and the taint rules.

### E5. MCP: one blocking call and a schema-first reply

- **`scan` runs to completion within its budget and returns the result.** It sends progress
  notifications while it runs. Under two minutes the agent gets the answer in the same turn,
  and past two minutes Claude Code backgrounds the call. A second `scan` on a workspace whose
  scan is running attaches to it and returns the same result, so a client with a short timeout
  still works and needs no separate protocol.
- **The structured reply is the product**, because it is what Claude Code's model reads. It
  should be a small, stable schema: state, verdict, reason, complete, scope, counts, grouped
  findings with evidence and fix, what did not run, and next steps. Include a `report` field
  holding the Markdown summary, so the text reaches the model too. Keep it under the 25,000
  token limit.
- **Tools:** `scan`, `scan_cancel`, `findings` (today's list and explain, filtered by
  fingerprint, rule or path), `doctor`, and a new `update` that fetches the database and index
  and says so. `scan_status` stays only as an alias that attaches.
- **Inputs:** the workspace defaults to `CLAUDE_PROJECT_DIR` or the client's first root. It
  must exist, be a directory and lie inside the client's roots, or the call fails with
  `isError` and one sentence. Every schema has `additionalProperties: false`. Errors carry a
  `kind`, and `doctor` is suggested only for the kinds a precondition explains. This closes C2,
  C3, C4, C7 and N5 by construction.

### E6. Lifecycle guarantees that do not depend on the happy path

- Label every container with the scan's generation and the owning process ID. At every scan
  start and in `doctor`, remove containers whose owner is dead.
- The server exits on stdin EOF and on parent death. It polls `getppid()`, because macOS has no
  parent-death signal. Shutdown kills by label and is bounded at three seconds.
- The workspace lock records its holder's PID, so *Busy* can say whether the holder is alive.

### E7. Fresh data without a terminal

A scan refreshes a **stale** database and index the way it already fetches **absent** ones:
announced, and recorded in `run.json` under `network.fetched`. Data comes in and nothing leaves.
An explicit `fetch = "never"` setting serves air-gapped users. This amends task 14.2 and needs
the owner's approval under `CLAUDE.md` §10, as 24.1 did for absent data.

### E8. A report worth trusting

- **Group** by rule and directory: one entry with a count and its locations. This fixes C9 and
  the eight pin lines. Rank a flood of one rule in one data directory below distinct findings.
- **`SUMMARY.md` leads** with the verdict, the scope manifest and the top groups. The agent
  instructions move to the end and shrink, because the MCP handshake already carries them.
  Titles are never cut mid-word.
- **Add the checks the audit showed are missing and in scope:** local agent configuration
  holding absolute paths or credentials that git does not ignore (an AI Artifact Check rule),
  and workflow permissions (zizmor).
- Keep everything that already earns trust: complete or incomplete, not re-checked, coverage
  notes, tool and database versions, `left this machine: nothing`.

## 6. Recommendations: the process

- **P1. Acceptance before architecture.** Build a scripted acceptance set and run the current
  engine through it first, as the baseline. Repositories:
  1. The gate's shape: a few hundred source files, a large ignored data directory and a `.venv`.
  2. A lockfile with known CVEs (`broken-repo`).
  3. A secret committed and later removed, so it exists only in history.
  4. Nested directories named `archive` and `build` holding planted issues (N1, N2).
  5. `terraform-aws-vpc`, for infrastructure parity.
  6. This repository.

  Run each on a Mac with a 4 GB Docker Desktop VM and on Linux. Measure wall time, whether the
  expected findings came out, containers alive afterwards, and one `claude -p` sentence per
  repository scored on turns, cost and whether the report was right.
- **P2. A Mac in the loop.** GitHub's macOS runners cannot run containers (measured on
  2026-09-22). A self-hosted runner on a spare Mac, or a scheduled local script, runs the
  acceptance set nightly.
- **P3. Fakes that model the runtime, or fewer fakes.** Of 1,096 test functions, 37 are marked
  end to end and about 33 of those drive a real runtime, only on Linux with native mounts. No fake models a cancel while Scanners
  are queued, and the cancel test's fake ran Trivy after the cancel without anyone checking.
  Two unit-test fakes set a Docker path and so call the real `docker info`, which makes their
  fleet width depend on the host. E1 leaves far less to fake: one process, one kill.
- **P4. Test behaviour, not wording.** 69 test functions compare against literals of six words
  or more. About 22 more read prose documents, and about 50 read the text of workflows or the
  Dockerfile. Keep the supply-chain checks. Replace sentence matching with checks on fields
  and kinds.
- **P5. Documents an agent can hold.** `CLAUDE.md` is 68 KB, about 17,000 tokens loaded into
  every session, and most of it is a history paragraph. `tasks.md` is 600 KB, about 150,000
  tokens, and no agent can read it. Code is 28% comments and docstrings, much of it narrating
  history. Proposal: `CLAUDE.md` under 200 lines of rules, locked decisions and current focus.
  History moves to `CHANGELOG.md` and `docs/history/`. `tasks.md` is archived and replaced by a
  short milestone file whose every task has a measurable exit on the acceptance set. Comments
  state invariants and reasons; the story lives in git and the ADRs.
- **P6. Triage outside findings against the goal.** A review item becomes a task only if it
  moves R1 to R8 or a supply-chain property. Everything else goes to a backlog.

## 7. Release recommendation

**Do not tag `1.0.0` now.** A `1.0` promises the stability of the MCP schema and the
shim/image protocol, and E1 and E5 change both. Tagging now would spend the number on an engine
this review recommends replacing.

1. Cancel run 36317791899, which is held at the brake.
2. Ship **`0.6.0`** within a day for current users. *Amended when the plan was written:*
   `0.6.0` rather than `0.5.1`, because `main` already carries additive MCP schema changes,
   which this project's precedent makes a minor. The release carries: refuse a missing or relative workspace
   (C2); cancel queued futures and check the flag before each launch (C1's minimal fix); report
   skipped built-in directories by name (N2's minimal fix); correct the README's git-history
   claim (N4). The version on `main` returns from `1.0.0` to `0.6.0`.
3. Reserve **`1.0.0`** for the rebuilt engine, once the acceptance set passes on both
   platforms.

## 11. Follow-up questions, answered (2026-09-27)

The owner asked five questions after accepting the review. Each answer is a recommendation.
The decisions it leaves open go to the grilling session, whose answers become ADRs and
`CONTEXT.md` entries.

### 11.1 How to simplify without losing impact or features

**The impact is four things:** the provable offline guarantee, the AI-specific Checks, an
honest agent-readable report, and supply-chain trust. Everything else is cost, and most of the
cost has accumulated around the engine.

| surface | today | after the plan | where |
|---|---|---|---|
| containers per `offline` scan | 6, plus a probe | 1 | 33 |
| ways to exclude a path | 6 flag dialects, a generated Gitleaks config, a built-in list, a gitignore opt-in | 1 File Set | 33 |
| Scanners run on an application repository | 6 plus the Checks | 4 plus the Checks: Gitleaks, Trivy, Opengrep, zizmor; Checkov only where there is infrastructure (11.6), Syft replaced by Trivy's report | 34 |
| MCP tools | 6, with a poll loop | 5, one call returns the result | 36 |
| CLI commands | 9 | 7: `explain` folds into `findings`, `cache` into `doctor` and `update --prune` | 36.5 |
| environment variables | 16 | about 6 for CI and mirrors; the rest become settings in two files | new |
| status reply | text and fields written separately, and they disagreed (C4, C7) | fields first, text rendered from them | 36.2 |
| documents in `docs/` | 9, plus `council/` and `gates/` | 4 plus the ADRs: `EVALUATING`, `RELEASING`, `PROTOCOL`, `AIR-GAPPED`; closed reviews, gates and the council's files move to `docs/history/` | 37.2 |

Three further simplifications need a measurement first:

- **One vulnerability source instead of two.** OSV-Scanner can use a downloaded offline
  database, which would bring it onto the `offline` Profile and could replace Trivy's
  database for language dependencies. `full` would then mean only the registry questions
  and EPSS. The spike belongs beside 34.1.
- **The SBOM on request.** No finding depends on it. If it comes from Trivy's pass it costs
  nothing, and it stays. If it costs a pass, make it `--sbom`.
- **Settings in two files.** Project policy lives in `.security-scan.toml`: scope, excludes,
  suppressions, profile, budget, fetch policy. Machine settings live in one user file:
  runtime, mirrors, cache. Environment variables remain only as overrides for CI.

**Rejected, because each loses impact:**
- *Native binaries instead of a container.* They lose the kernel-enforced offline proof and
  the structural read-only guarantee on macOS.
- *Dropping the Name Index.* It is the one AI-specific check that works offline.
- *Dropping SARIF.* `valvur-action` and the IDEs consume it.
- *Merging the two Profiles.* The network boundary is the product.

### 11.2 Is an AWS container deployment worth it?

**Verdict: do not build an AWS service. Do make the image runnable as a pipeline step, which
the rebuild gives almost free.** Three shapes, judged:

1. **A hosted service that valvur runs.** This breaks the moat outright: code goes to a
   vendor. No.
2. **A scan service in the customer's own AWS account**, which agents on laptops send code
   to. Code leaves the laptop, and the service needs authentication, a network listener
   (ADR-0015 chose stdio precisely to have none), multi-tenancy and retention rules. That is
   a second product. What it would buy, relief for small laptops, is gone once a scan takes
   8 s. No, unless a paying customer asks for it.
3. **The image as a job in the customer's own pipeline**: CodeBuild, an ECS task, a
   Kubernetes job, a GitHub or GitLab runner. Nothing leaves the customer's account, and
   the scan runs where the code already is. Today this is blocked because the shim must
   launch containers, and Fargate has no Docker socket (F1.10). Once the engine runs inside
   the image (E1), the image's entrypoint can scan a mounted or cloned checkout directly.
   **Yes, after `1.0.0`**: one entrypoint mode, one CI test, one page of documentation.
   It satisfies F1.10's standing half, *no cloud-specific code path*, and a measured run on
   CodeBuild or ECS is the evidence F1.10 names for reviving its deferred half.

**Does shape 3 break local-only?** No, if "local" is stated as what it means to the target
market: *on infrastructure the user controls, with no vendor in the path*. The laptop path
stays primary.

One AWS benefit is available today: **ECR as the air-gapped mirror** for the image, the
database and the index. The mirror settings exist. Test the mirror once against ECR and
document it in `AIR-GAPPED.md`.

### 11.3 The local equivalent of an IaC template

A local tool's infrastructure is the runtime on the machine, the pinned version, the data it
needs, the client wiring and the project's policy. Mapped onto Terraform's concepts:

| Terraform | valvur | status |
|---|---|---|
| `main.tf`, the committed desired state | `.security-scan.toml` for policy, plus the client file (`.mcp.json`, `.kiro/settings/mcp.json`) with a pinned version | exists; the pin is not recommended anywhere yet |
| the lock file | the version pin in the client file; the image follows it by protocol major | exists |
| `validate` | a JSON Schema for `.security-scan.toml`, which editors use through Taplo and `doctor` checks | new, small |
| `plan` | `valvur doctor`: what is missing and the fix | exists |
| `apply` | `valvur init`: the client file for each client found, a starter `.security-scan.toml` with excludes suggested by the pre-flight count, then the image, database and index fetched | new |
| state | `state.json` and `run.json` | exists |

**Recommendation:** add `valvur init` and the schema, and write nothing new beyond that; a
DSL would be cost with no reader. One constraint needs a decision: `init` writes files into
the project, and `CLAUDE.md` §10 forbids writing to the scanned tree without the owner's
approval. `valvur suppress` already solves the same problem by printing and never writing.
So `init` prints by default, and `--write` exists only if the owner approves it. For teams, a
`devcontainer.json` snippet and one line for Homebrew or `mise` in the README cover the
machine half.

### 11.4 What to borrow from existing projects

Every licence below was checked against the project's own repository or Homebrew's formula
data, and each capability against its documentation, on 2026-09-27. ADR-0005 rules out GPL
and AGPL code in the image. ADR-0008 rules out anything that needs an account or sends data.

**Adopt: these enter the image or its data.**

| project | licence | what we take | where |
|---|---|---|---|
| **zizmor** | MIT | GitHub Actions audits, including `unpinned-uses`, `excessive-permissions` and `template-injection`. It is a Rust binary of about 9 MB, with `--offline` and SARIF or JSON output. Five of its roughly 40 audits need GitHub's API and are off offline. | 34.2 |
| **ossf/malicious-packages**, through OSV-Scanner's offline database | Apache-2.0 data | 238,451 known-malicious package reports in OSV format across eleven ecosystems. It closes the hole the existence check leaves once an attacker registers a hallucinated name. Whether OSV-Scanner reports these `MAL-` entries offline is unverified and is the spike's first question. | 34.1 |
| **Trivy's `convert`** | Apache-2.0, already in the image | The SBOM from the JSON report of the pass we already run, instead of a Syft pass. | 34.4 |

**Borrow a design; take no code.**

- **MegaLinter**, AGPL-3.0, so ideas only. Its timeout model is the one 33.4 needs: a
  per-tool timeout that kills the whole process tree, reports exit 124, lets the others
  continue, and can be overridden per tool. **Super-Linter** (MIT) shows the per-tool
  stdout, stderr and exit-code files that 33.4's manifest can mirror.
- **aquasecurity/trivy-mcp** (MIT) and the archived **semgrep/mcp** (MIT) both make the scan
  one synchronous call. trivy-mcp returns a batch id, severity counts and a `next` hint
  naming its findings tool, then pages findings. That is 36.2 and 36.3's shape, already
  proven by two vendors.
- **OpenSSF Scorecard** (Apache-2.0) has local checks for a security policy, a dependency
  update tool, token permissions, dangerous workflows and binary artifacts. Its
  vulnerability and fuzzing checks reach the network, so do not bundle it. Two of its local
  checks match what the owner's manual audit of the lab found and valvur did not: no
  `SECURITY.md` and no Dependabot. Whether repository hygiene is in scope is a grilling
  question.
- **cisco-ai-defense/mcp-scanner** (Apache-2.0) runs its YARA analyzer locally, and its
  rules cover prompt injection, coercive injection, exfiltration and credential harvesting.
  They are candidates for the AI Artifact Check's directive detection, measured for false
  positives on the corpus before any is adopted. **snyk/agent-scan**, formerly Invariant's
  `mcp-scan`, needs `SNYK_TOKEN` and sends content out, so only its public risk taxonomy is
  usable.

**Evaluate as alternatives in the 34.1 spike.**

- **KICS** (Apache-2.0) covers Terraform **and** GitHub Actions, including run-block
  injection and unpinned actions. That makes it the only single candidate that could replace
  Checkov outright. Its latest releases ship as Docker images only, with binaries last
  attached at v2.1.20, and it publishes no speed figures, so measure both.
- **poutine** (Apache-2.0) adds GitLab, Azure DevOps and Tekton pipelines and an
  untrusted-checkout rule. Its offline behaviour is undocumented. Consider it only if users
  ask for CI systems other than GitHub.

**Reject.**

- **actionlint** (MIT): zizmor covers its injection check, and its shellcheck integration is
  GPL-3.0.
- **GuardDog** (Apache-2.0): it downloads packages to analyse them, so it can never run on
  `offline`.
- **detect-secrets** (Apache-2.0): its baseline is what valvur's Suppressions already do, and
  its last release was in May 2024.

### 11.5 Should we run a grilling session?

**Yes, now, before Phase 33 starts.** Phases 31 and 32 do not depend on it. Phase 33 does,
and so do the five ADRs the plan names. The branches to walk, in dependency order:

1. **The File Set:** are untracked files git does not ignore scanned by default? What does
   a directory that is not a repository get? Which ignored agent files are always included?
2. **History:** on by default? All refs or the current branch? What bounds, in commits and
   bytes?
3. **Freshness:** refresh stale data inside a scan by default? For whom is `fetch =
   "never"` the default?
4. **The blocking `scan`:** the default budget, and what the agent receives past it.
5. **The Scanner set:** what parity replacing Checkov must show, and whether OSV's offline
   database is in scope.
6. **The Results Folder:** is the SBOM on by default? Is SARIF?
7. **`init`:** print only, or write with approval?
8. **The pipeline entrypoint:** before or after `1.0.0`?
9. **People and machines:** who takes the gate; whether a Mac is available as a runner.
10. **`1.0.0`:** the criteria, written as acceptance-set results.

### 11.6 Two measurements taken while answering

**Trivy is not a drop-in replacement for Checkov.** On `terraform-aws-vpc`, in the image,
twice:

| | failed checks | distinct rules | seconds |
|---|---|---|---|
| Trivy, `--scanners misconfig` | 24 | 3 | 7 to 10 |
| Checkov | 51 | 9 | 77 to 83 |

Trivy is about nine times faster and finds a third of the rules. It also does not read
GitHub Actions workflows at all: its misconfiguration scanners are Terraform, CloudFormation,
ARM, Dockerfile, Kubernetes, Helm and Ansible. **So E4 is amended:** zizmor takes the
workflows, and Checkov stays for infrastructure. Checkov then runs only where a repository
has infrastructure files other than workflows, which removes it from most application
repositories, the case measured at 14.4 s of a 20 s scan on the Mac. Replacing Checkov stays
open for KICS in the spike.

**Trivy reports usage data when it has a network.** With a network, `trivy fs` logs
*"Running version check and sending anonymous telemetry"*. valvur passes neither
`--disable-telemetry` nor `--skip-version-check`. It does not leak today, for two reasons:
every Trivy scan runs with no network, and the one networked Trivy command, the database
fetch, logged no telemetry when run to completion. But the networked container that 33.7
creates for `full` would start sending it silently if Trivy ever ran there. 33.7 now requires
both flags on every Trivy call, with a test.
