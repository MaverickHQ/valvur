# Review, 2026-10-03: the architecture, and what a 2.0 would change

Written after `1.3.1`, at the owner's request: review the solution approach and the
architecture rather than the functionality, and recommend how to improve 1.x or what a
version 2 would change. The owner accepted it the same day and asked for its 1.x steps as
phases: R23, R24 and a reshaped R20 in [`tasks.md`](../../.kiro/specs/valvur/tasks.md)
(D50 to D57). The evidence is the tree at `7b26d77`: the import graph read from the AST,
one scan traced from both surfaces to the Results Folder, and the tests, CI and release
measured. Line references are to that commit.

## 1. Verdict

**Keep the outer shape; do not rewrite.** The boundaries that make valvur what it is are
right, and they are why the moat holds. The debt is in two places:

- **Inside the host side.** It has no layering, and several core concepts are modelled
  more than once.
- **In the machinery around the product.** It welds three release cadences into one
  artifact, and it now costs more to maintain than the scanner it surrounds.

The recommendation is a 1.x release that restructures the inside with no contract
change, and then a 2.0 that changes three contracts (§5).

## 2. What to keep

- **The sealed Scan Container, fed a Snapshot** (ADR-0022). The source is never mounted,
  and `offline` has no network interface. The guarantee is structural, not a policy.
- **A host that orchestrates and an engine that decides nothing,** behind a versioned
  protocol: [`PROTOCOL.md`](../PROTOCOL.md) and the image's `org.valvur.protocol` label.
- **The findings model.** A frozen `Finding`, identity per class (ADR-0003) and
  `fp_version`. Each artifact has one consumer (ADR-0002). One generation is renamed into
  place, `run.json` last.
- **A host side on the standard library alone,** and the signed data artifacts on GHCR:
  candidate, pulled back and verified, then tagged.
- **The Score and its ratchet** (ADR-0026). It is the best part of the process: a fitness
  function every change answers to.

## 3. Inside the host side

### 3.1 No layering

- **The package's `__init__` loads the orchestrator.**
  [`valvur/__init__.py`](../../src/valvur/__init__.py) imports `api` to re-export `scan`.
  Python runs a package's `__init__` before any of its modules, so every `from . import x`
  loads `api` first. Importing `valvur.hook` loads 52 of valvur's modules, `api` among
  them, when it needs a command parser and the index reader. Measured: 0.11 s, against
  0.01 s for a bare interpreter, paid on every install the plugin's hook checks.
- **Cycles.** Counting that edge, the 52 modules form one cycle. Without it, two remain:
  ten modules around `api`, `engine_host` and `runner`, and six around `doctor`,
  `operations` and the MCP server. Six of them (`api`, `pipeline`, `provenance`,
  `results`, `staleness` and `summary`) form a cycle at import time. The others are held
  apart by deferral: 233 imports sit inside function bodies.
- **The orchestrator keeps growing.** [`api.py`](../../src/valvur/api.py) was 716 lines at
  [the review of 2026-09-23](REVIEW-2026-09-23.md) (A3) and is 1,245 now. It imports 34 of
  valvur's modules. Its two working functions, `_engine_fleet` and `_assemble`, are 154
  and 135 lines, and between them they cover the plan, reuse, the Snapshot, history, the
  network split, the manifest, the budget's bookkeeping, the fixed and not-rechecked diff,
  and the `ScanRun`.

**Recommendation:** four layers, each importing only from the ones below.

| layer | holds | I/O |
|---|---|---|
| `core` | the Finding, identity, the verdict, ranking, path classes | none |
| `app` | one scan service, the read models, jobs | through `infra` |
| `infra` | the container runtime, the datasets, the registries, git | yes |
| `surfaces` | the CLI, the MCP server, the hook | stdio |

A check in `verify.sh` holds the direction, deferred imports included. The package's
`__init__` exports lazily, so `from valvur import scan` keeps working without loading
anything.

### 3.2 No single scan service

- The CLI calls `api.scan` directly (`cli.py:668`). MCP goes through `operations`, then
  `mcp/jobs`, then a thread.
- One scan therefore gets three summaries:
  - the CLI's, from the in-memory `ScanRun` (`cli.py:678-714`);
  - the MCP reply's, from re-reading the files the scan just wrote (`reply.py:138-199`);
  - a third, `operations._summarise`, stored in `Job.summary` (`mcp/jobs.py:184`) and
    read by nothing.
- `operations` and `reply` are meant to be independent of the surface. Both import
  `valvur.mcp.jobs` (`operations.py:19-20`, `reply.py:20-21`), and `operations` reads the
  MCP call's thread-local state.

**Recommendation:** one scan service that both surfaces call, one read model of its
result, and a renderer per surface. The MCP reply's schema and the CLI's text are
unchanged.

### 3.3 The same concept, modelled many times

This is the clearest signal in the code, and it is where drift comes from.

| concept | copies |
|---|---|
| whether data is stale | about 12 code paths, with thresholds in four modules and a literal in `provenance.py`. A scan refreshes the Name Index past 2 days (`api.py:416`); `update --if-stale` only past 30 (`updating.py:46-55`), and, while the database is current, leaves KEV and EPSS alone |
| whether a Finding is active | 6: `api`, `summary`, `remediation`, `gate`, `reply`, `grouping` |
| whether a tool may use the network | 4: the Check adapter, OSV's adapter, `Invocation.network`, and `VALVUR_NETWORK` |
| launching a container | 2 runners, `runner.ContainerRunner` and `engine_host.ContainerRuntime`, each with its own flag builder |
| `.security-scan.toml` | parsed at seven call sites in one scan; the File Set is rebuilt during coverage rather than passed along |

**Recommendation:** name each concept once.
- **A table of datasets:** source, verifier, age reader, refresh threshold, `inconclusive`
  threshold and mirror setting. Scan, `update`, `doctor`, `run.json` and the reply all
  read it.
- **One predicate for active.**
- **The network grant as one field,** which the engine turns into the environment for each
  tool, in every runtime.
- **A scan context** built once (the File Set, the project's configuration, the settings)
  and passed through.

### 3.4 Strings and duck types inside

- The engine emits structured events. `api` turns them into prose (`api.py:850-860`), and
  `reply` parses the prose back by prefix (`reply.py:112-119`). Budget state is recovered
  from the prefixes of reasons.
- `api` asks the runner what it supports with 11 `getattr` calls. Adapters carry members
  outside their Protocol (`version`, `artifact`, `offline`, `history_command`), found the
  same way.

**Recommendation:** typed events, and complete `Runtime` and `ScannerAdapter` Protocols,
so mypy checks what tests now pin by hand.

### 3.5 Invariants that lapsed when the architecture moved

Found by reading, not by a run. Each was a comment, not a type or a test, so nothing
failed when ADR-0022 put every tool in one container.

- **Executable `/tmp`.** `Invocation.allow_exec` says it is "granted per Scanner, never to
  the fleet" (`invocation.py:83-85`). The Scan Container gives it to every tool
  (`engine_host.py:374`), because Opengrep unpacks itself there.
- **`full` inside the image.** In the pipeline-step mode, `VALVUR_IN_IMAGE=1`, the runtime
  never sets `VALVUR_NETWORK` (`engine_host.py:227`); only the container flags do
  (`egress.py:128`). So on `full`, dependency-reality behaves as offline there, and the
  registry questions are skipped.
- **The cache's precedence.** `XDG_CACHE_HOME` overrides `VALVUR_CACHE` (`cache.py:49`).
  The more specific setting should win.
- **The Profiles.** Both list the same ten Scanners (`profiles.py:33-51`), so `select`
  filters nothing and `run.json`'s `scanners_not_run` is always empty.

## 4. The machinery around the product

### 4.1 Three release cadences in one artifact

The image carries the Scanner binaries, the rules, the Checks and the whole valvur
package, held to the host's source tree by a hash.
- A urllib3 advisory in one of Checkov's dependencies stopped `1.2.0` for a day (#171).
- A rule change needs a full release: multi-architecture, signed, attested, and tested
  again on the artifact.
- A Scanner's version is stated in about five places: the Dockerfile, its adapter, the
  conftest's pins, the fake runner and the golden files' names.
- `prepare_release.py` edits 15 files per version, and the version string is in 19.

**Recommendation (2.0):** three artifacts, versioned apart.
1. **The host side,** on PyPI.
2. **The Scanner image,** versioned by protocol, so it can be rebuilt for an advisory
   without a host release.
3. **The rules and Check data,** a signed OCI artifact on the Name Index's path
   (candidate, measured, tagged), tagged only when the Score holds.

The host accepts a compatible range and records the exact digests in `run.json`, so a
scan stays reproducible.

### 4.2 Parsing sits on the wrong side for that split

Every adapter parses its tool's raw format on the host, which ties the host to the tool
versions inside the image. Adding zizmor (`adfb377`) changed 18 files.

**Recommendation (2.0, protocol 3):** the engine emits valvur's normalised findings. The
host validates them against the schema and still neutralises the evidence. Knowledge of a
tool lives with its version, and a new Scanner changes one artifact.

### 4.3 The documents are executable, so every change pays twice

- About 27,000 lines of documents against 20,000 of source; 29% of commits are `docs:`.
- 48 tests read prose and about 30 read other files' source text. 138 of 197 test modules
  open with a task ID rather than the module they test, and `src` holds 865 task,
  decision and ADR references.
- The traceability check reads 16,500 lines of `docs/history`.
- Prose still drifts: `CLAUDE.md` and `RELEASING.md` said six required checks while
  GitHub enforced eight (corrected with this review).

**Recommendation:**
- Generate what must match the code: the tools reference, `PROTOCOL.md`'s tables, the
  settings and their variables, the CLI's help, the Scanner pins. One test holds every
  generated block current; the tests that compare prose go.
- New tests are named by module, and new code cites ADRs, not tasks.
- Keep the Score, the acceptance set and the supply-chain constraints exactly as they are.

### 4.4 CI builds the same image five times

A pull request builds the image five times: e2e on two architectures, two reproducibility
builds, and the self-scan. A release then runs the suites three times. Seven copies of the
issue-on-failure step sit across six workflows, and twelve inline `grep`s read the
version.

**Recommendation:** build once per commit and architecture; the e2e, the self-scan and
the first reproducibility build use that image. Composite actions replace the copies.

## 5. Version 2

Beyond §4.1 and §4.2:

- **Path classes.** The File Set classifies each path once: source, test, fixture, docs,
  example, vendored or generated. Findings carry the class, and one policy table decides
  what a class changes. D47 as first written applied the idea three times, in three
  places. This one is 1.x work: R20 is reshaped around it (D56).
- **Reuse by declared inputs.** ADR-0030 generalised: every Scanner declares what it reads,
  and its result is reused while those inputs, the tool, the data and the rules are
  unchanged. zizmor reads only workflows and Checkov only infrastructure files.
- **One settings model.** The source names 22 `VALVUR_*` variables; [the review of
  2026-09-27](REVIEW-2026-09-27.md) aimed for about six. Two files, the project's and the
  machine's, with environment variables only as overrides and the precedence tested.
- **The MCP specification.** The hand-rolled server (ADR-0015) speaks `2025-06-18`.
  Hand-rolling is right, but each revision needs a planned task. If clients adopt the
  newer revision's asynchronous tasks, revisit ADR-0024's blocking `scan`.

## 6. What not to do

- **A rewrite.** The outer contracts are right; a refactor under the Score gets there.
- **Native binaries instead of the container.** That loses the kernel-enforced proof that
  a scan is offline, as the review of 2026-09-27 found (§11.1).
- **A daemon or a watcher.** That breaks `CLAUDE.md` §4.

## 7. The order, as accepted

1. **R23, the host side in layers** (D50 to D54). Internal only: no contract changes, the
   Score unchanged on both lanes.
2. **R24, the machinery made lighter** (D55). Generated documents, one version source,
   CI that builds once.
3. **R20, reshaped around path classes** (D56), then R21 and R22 as written, and R19 at
   its date.
4. **2.0** (D57): the three artifacts, protocol 3, reuse by declared inputs, the settings
   model. Planned after R24's exit, each part with its ADR, when the owner asks.

## 8. How it was measured

- **The import graph:** every `import` in `src/valvur` from the AST, top-level and
  deferred, with and without the package's own `__init__` as an edge; strongly connected
  components for the cycles.
- **The hook's import cost:** `python -X importtime -c "import valvur.hook"`, and three
  timed runs against a bare interpreter, on this Mac.
- **Function lengths, comment density and environment variables:** from the AST and
  `grep` over `src/valvur`.
- **The scan:** traced from `cli.main` and from `server.main` to `results.write`, by
  reading.
- **Tests, CI and the release:** counted over `tests/`, `.github/workflows/` and
  `scripts/`. The required checks were read from GitHub's branch protection.
