# Phase R3, one scan, one container: the record

## What the phase changed

Every Scanner runs in one Scan Container per network boundary, fed a Snapshot of the
File Set on stdin; the source tree is never mounted (ADR-0021, ADR-0022). The
thread-pool fleet, the per-Scanner containers, the Checks batch, width from memory,
the six exclude dialects, the built-in vendored list, the generated Gitleaks config,
`honour_gitignore`, the unreadable-workspace probe and the in-process container
registries are deleted. Secrets are read from git history. Protocol 2; `0.7.0` is
prepared.

| file | on `main` | at the phase exit | change |
|---|---|---|---|
| `api.py` | 959 | 1,023 | +64 |
| `runner.py` | 692 | 513 | −179 |
| `exclusions.py` | 436 | 134 | −302 |

`api.py` and `runner.py` together are 115 lines shorter. The engine lives in modules of
its own: `engine/` (205 lines), `engine_host.py` (347), `fileset.py` (257), `history.py`
(104) and `owner.py` (93).

## Defects the phase found in its own new path

Each was found by a test written for the new path or by this exit run, and fixed test
first.

- A `full` scan through the Scan Container gave every tool, Trivy included, the network
  (R3.8).
- The engine path read "nothing to scan" as a failure and a missing report as a pass.
- An adapter that refused to build its command raised out of the scan, where the fleet
  had failed that Scanner alone.
- A cancel counted the tools it killed as finished.
- The Scan Container's own mounts carried no SELinux label.
- A tool killed by a signal was recorded as −9, not 137, so an OOM kill did not read as
  one.
- The local runtime's SIGKILL left tools running in their own process groups (R3.5).
- Opengrep skipped `build/`, `dist/`, `vendor/`, `test/` and `tests/` of its own accord,
  so a flaw in `mypkg/build/` went unread; repository 4 caught it on the first exit run.
- The lifecycle probes passed without measuring anything: their 30,000-file folder was
  refused before a container started. They now need a Scan Container to have run.
