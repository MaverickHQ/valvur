# Phase R41, model output reaching a sink, measured: the record

Built in a local session on 2026-10-11, after `1.5.2`, at the owner's word (D80). valvur's
four rules for model output reaching a sink are its core claim for AI-generated code, and
until R41 no track held a case of their weakness: `docs/RULES.md` called them
*unmeasured*. R41 adds a ninth track, `llm-output`, and measures them on it.

## The real cases (R41.1)

Five published advisories in LLM frameworks, each MIT-licensed, pinned at its vulnerable
commit in `tests/eval/sources.toml` and fetched into the build cache, as the corpus is.
Only LangChain's math chain has a clean fixed commit; the others moved, were bypassed or
were never fixed.

| case | advisory | sink | the LLM rules | the INFO inventory |
|---|---|---|---|---|
| LangChain `LLMMathChain` | CVE-2023-29374 | code, via `PythonREPL` in another module | none | none |
| LangChain `PALChain` | CVE-2023-36258 | code, via `PythonREPL` | none | `dangerous-exec` |
| LangChain `SQLDatabaseChain` | CVE-2023-36189 | a query, via `SQLDatabase.run` | none | none |
| LlamaIndex `PandasQueryEngine` | CVE-2023-39662 | code, in `default_output_processor` | none | `dangerous-eval`, `dangerous-exec` |
| Vanna `get_plotly_figure` | CVE-2024-5565 | code, passed in by its caller | none | `dangerous-exec` |

PandasAI's CVE-2024-12366 is left out: its repository's licence reads `NOASSERTION`. In
every case the flow crosses a function, a class or a module. Opengrep's taint is
intra-procedural, as the rules' header states, so none is reported.

## The track (R41.2, R41.3)

- **Generated twins:** 34 vulnerable cases and 34 fixes, from a fixed seed. Code
  execution, a shell and a query each come from the eight Python SDK families the rules
  name; the DOM from the six JavaScript ones. Every sink a rule lists is written somewhere,
  and one flow per sink goes through a helper, the shape the rules are known to miss.
- **Scored per sink** by the OWASP Benchmark's formula, as tracks 1 and 2 are, with the
  generated and the real cases reported apart as well as together, since valvur writes its
  own twins.

## The rules, measured (R41.4)

- **Each of the four is at precision 1.0** on track 9: 8, 8, 8 and 6 true, none false.
  `docs/RULES.md` has a track 9 column, and no rule there is *unmeasured* for want of a case.
- **One rule fixed.** `valvur.llm.output-to-sql` flagged all eight fixes, each binding the
  model's text as a parameter, the form its own message recommends: its sink was any
  argument of `execute`. It is now the query argument alone, held through the image by
  `test_llm_sql_sink.py`, and the query sink rose from 0.0 to 80.0.
- **What precision does not show is misses.** The rules catch 30 of the 34 generated flows,
  none of the four through a helper, and none of the five real advisories.

| sink | caught | missed | fixes flagged |
|---|---|---|---|
| code execution | 8 | 5: a helper and four advisories | 0 of 10 |
| a shell | 8 | 1: a helper | 0 of 9 |
| a query | 8 | 2: a helper and an advisory | 0 of 9 |
| the DOM | 6 | 1: a helper | 0 of 7 |

## Found on the way

ClusterFuzzLite failed on #224, a docs-only pull request: a `.security-scan.toml` of arrays
nested about a thousand deep, two kilobytes, makes Python's `tomllib` raise
`RecursionError`, which no reader caught, so one committed file could end a scan. Fixed in
`669ed84`: `toml_input.loads` is the one call to `tomllib` and answers *too deep* as a
parse error, for the fifteen places the Workspace's TOML is read. JSON fails the same way
only past 100,000 levels, and is left for its own task. Nothing in detection changes, so
the exit's images, built before it, stand.
