## What the checks caught

- **The wording test caught its author.** R51.3 wrote *"A mapping is not coverage"* into
  SARIF's taxonomy description. A denial that names the thing is one edit from a claim, so
  the sentence now says what a mapping is.
- **The table cost a small repository its screen.** Written whenever there are active
  Findings, as designed, it took a two-Finding summary from 45 lines to 53. It is written
  when it sorts something. The owner may prefer the design's.
- **A full disk looked like a regression.** Two container tests failed at R51.3's commit
  and not on the change: the dev machine's Docker volume was 96% full of build cache.

## The imports, measured

`scripts/imports_measure.py` sends `results.sarif` to DefectDojo and `sbom.cdx.json` to
Dependency-Track through each tool's own API, as a user's pipeline would, and reads back
what arrived. Then it sends the same file again. valvur itself uploads nothing.

- **The tools:** DefectDojo 3.5.202 and Dependency-Track 5.2.2, each started from its
  published images, every one pinned by digest in `.github/imports/`. Both start in under
  a minute.
- **The scan:** `tests/fixtures/broken-repo`, with the SBOM asked for, and with the two
  things a real project sends that the fixture lacks: a Suppression for one advisory, and a
  `.trivyignore` naming another with no reason and no expiry, which valvur does not accept
  and reports as a live Finding.
- **Where:** the dev machine, Amazon Linux 2023 on arm64, with the workflow's own compose
  files and script. **Not by a dispatched run of `imports.yml`:** GitHub dispatches a
  workflow only once it is on the default branch, and this phase has not landed. The
  amd64 lane is that workflow's first run after it lands.

### What was corrected

One thing a user needs was lost, and it is corrected inside SARIF (R51.7): an ignore of the
project's own that valvur did not accept is no longer a suppression with `status: rejected`.
It is `properties.ignoredBy` on the result, and a `suppressions` entry means an accepted
risk, always.

What was measured and is left as it is, each stated in the guide:

- **The Fingerprint is missing on a Finding found through two lockfiles.** SARIF gives a
  result several locations when each needs the change, which is the case here. Writing one
  location would keep the id and lose the second lockfile in DefectDojo, the worse loss. A
  re-import matches those findings without the id.
- **An accepted risk arrives marked a false positive.** That is DefectDojo's reading of
  SARIF's own field for a suppression, and SARIF has no other field to say it in.
- **A second import doubles the findings,** since DefectDojo installs with deduplication
  off. The guide's step is a re-import.
- **A dependency's package and version have no field** in DefectDojo's SARIF import. They
  are in the title.
